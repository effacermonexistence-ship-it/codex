## What v143 fixes

Live incident on v142 (Omar.system debug identity): the client ran the whole funnel, received the four-field checkpoint at 03:02:00Z, then restarted at 04:50:31Z with "Hi, can I please get more information?" and got, 88 s later, "which one should i fix the date the time or the name and number?".

1. Route. The direct-info route was guarded by the durable design-direction check, which reads the client-anchored reference from state, so any later information request lost the direct-info route; at the open checkpoint the turn fell to the confirmation wait, the generic-info fast path was refused there, the model lane exhausted three verifier passes and the route-aware recovery emitted the which-field revision ask. v143 treats a self-contained information request at the open checkpoint as a side question: the contract keeps the await stage under `side_question_info_request_keep_checkpoint_open`, the fast path is admitted under exactly that action and reason (one rule shared by the runner and the control-plane receipt gate), and the deterministic answer is one model-spot explanation plus one resume line that hands the thread back to the pending confirmation. No greeting, no design question, one pass.
2. Recovery. The await-stage route-aware recovery now asks which field only when the live turn carries revision evidence; an information request gets the side-question answer and anything else gets a rotating neutral nudge that keeps the checkpoint open.
3. Verifier rebase. When the verifier reports that the four fields are ready for the checkpoint while the route is still a post-form ask (the 03:01Z turn: route locked before the gmail form match landed, 53 s and three passes), the plan rebases to the checkpoint so the deterministic checkpoint authors the turn in one pass.
4. Executed-checkpoint state. When the adopted packet is the four-field block, the commit records the checkpoint as sent and persists the displayed identity, date and time regardless of the plan action (the 03:02Z checkpoint had left the stage hint at "awaiting form identity" under a visible open checkpoint).
5. A scheduling proposal ("Can we do September 5?") is never stored as design context.
6. Greeting rule at the checkpoint. The fresh-info-opener greeting rule treated the side question as the first assistant turn whenever the runner's bounded history window was empty and demanded a greeting, which is what re-greeted the client mid-thread on v142 and would have rejected the greeting-free side-question packet. It is now state-grounded: once the four-field checkpoint has been sent, the turn is never the first assistant turn. This guard was contributed by a parallel Claude session working the same incident and was verified on this tree.

Versions: closed-transition contract v74, generic-info fast path v2, route-aware visible recovery v6, contract-harness lock v117, hard harness lock v159, divergence harness v4 (adds the executed-path replay of the sanitized incident state through the real control plane and runner).
